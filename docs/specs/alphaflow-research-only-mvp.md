## Problem Statement

核心投资者需要在盘前、盘中、盘后和前瞻工作节奏中持续处理 A 股市场结构、资金、公司、新闻政策、预期与日历信息。现有行情终端能够提供大量数据，但不会替个人投资者持续完成跨来源规范化、证据核实、观点变化识别、个性化相关性判断、分发节奏控制和历史修订追溯。结果是用户必须在多个数据源、资讯渠道和研究笔记之间手工拼接事实，容易被重复资讯、无证据结论、过期数据和不可追溯的模型输出淹没。

AlphaFlow 已具备 TuShare/Python 数据能力、Minishare 资讯、证据上下文、研究工作流、Pi Agent Harness、确定性定时任务、Feishu 投递、首页不可变快照和 C++ 可靠任务运行基础，但这些能力尚未形成一个统一、可重放、可验证的主动研究信息系统。当前首页仍存在旧快照契约和 mock 数据语义，研究事件、冻结偏好、四维评估、研究收件箱、分级调度与全局资源许可也尚未完整落地。

MVP 必须解决的不是“做一条资讯链路”，而是让全部已确认能力在一致的领域语言和确定性控制下组成完整系统：零配置可用的专业市场基线必须保持全局完整，个性化研究雷达只能由用户显式研究关注增强；外部数据必须先成为可追溯的规范化对象；Agent/LLM 负责有界语义判断但不能拥有权威写入或发送权限；站内研究收件箱必须是主动分发的权威记录；所有历史、重试、降级和更正都必须可以解释和验收。

## Solution

AlphaFlow 为受邀核心投资者提供一个 `research_only` 的专业 A 股个性化研究信息系统：

- 以盘前、盘中、盘后和前瞻四个交易阶段组织完整的专业市场基线，并覆盖市场结构、资金与交易行为、公司信息、新闻与政策、预期变化、事件日历六类信息域。
- 使用版本化 Provider contract 将 TuShare、Minishare 及测试替身的结果规范化为来源断言、数据观测、数据观测修订及结构化覆盖结果，再通过两层首页数据清单生成不可变专业市场基线快照和个性化首页快照。
- 将新闻、公告、政策、问答及数据变化先形成研究事件候选，通过证据契约和单次 LLM 三态裁定产生已确认研究事件、暂缓候选或驳回记录，并通过不可变修订表达更正和撤回。
- 对研究事件修订执行重要性、置信度和信息增量全局评估，对每位用户执行相关性评估；LLM 返回分数、依据、引用和不确定性，代码执行确定性分发门控。
- 允许用户显式建立常规或重点研究关注，以独立的个性化研究雷达、排序、定时简报和紧急提醒增强体验，但不重排、删除或削弱专业市场基线。
- 以研究收件箱作为紧急提醒、定时简报、更正和撤回通知的站内权威记录；Feishu 只发送默认预授权、可关闭、可重试的提醒副本。
- 通过 Agent Runner 与 Deterministic Controller 两个主要 seam，在冻结输入、能力与预算内运行 Agentic Workflow；即时研究可直接使用当次公开网页证据回答用户，但后台产物只能消费已结算权威对象。
- 使用 PostgreSQL 权威的分级调度、任务生命周期、资源许可、背压、重试、熔断、降级、时效计量和审计，Redis 只提供至少一次唤醒，C++ Worker 只承担可靠执行而不解释业务语义。

## User Stories

1. 作为核心投资者，我希望无需先填写问卷或建立关注即可看到完整专业市场基线，以便立即开始当天研究。
2. 作为核心投资者，我希望按盘前、盘中、盘后和前瞻切换研究阶段，以便按照真实工作节奏组织信息。
3. 作为核心投资者，我希望在每个阶段浏览市场结构、资金与交易行为、公司信息、新闻与政策、预期变化和事件日历，以便完整扫描市场而不是只看资讯流。
4. 作为核心投资者，我希望看到市场广度、资金方向和关键事件节点的直观图表，以便快速建立方向感。
5. 作为核心投资者，我希望每项内容显示实际数据截止点和限制，以便区分当前事实、旧数据和降级结果。
6. 作为核心投资者，我希望盘中数据不足或尚未完成时延校准时明确显示降级，以便系统不会把旧快照伪装成实时状态。
7. 作为核心投资者，我希望新专业市场基线尚未生成时继续读取上一份可用快照，以便上游故障不会让工作台整体不可用。
8. 作为核心投资者，我希望可选数据失败时仍能读取标明限制的新快照，以便非关键缺口不会阻塞全部研究。
9. 作为核心投资者，我希望必需数据未达目标数据截止点时不生成误导性新快照，以便数据快速到达不等于数据已经完整。
10. 作为核心投资者，我希望所有数据值都能追溯到来源、原始记录、时间、单位和修订，以便核验研究依据。
11. 作为核心投资者，我希望重复抓取不会制造重复事实或重复历史，以便研究记录保持稳定。
12. 作为核心投资者，我希望上游更正能够形成新修订而不覆盖历史，以便知道过去看到的内容依据了什么。
13. 作为核心投资者，我希望新闻、公告、政策和异常数据先经过候选与证据核实，以便素材不会未经判断直接成为研究事件。
14. 作为核心投资者，我希望系统区分已确认事件、待核实变化和已驳回候选，以便不同事实状态不会混在一起。
15. 作为核心投资者，我希望待核实变化明确说明证据缺口、冲突和解除条件，以便我能判断是否值得继续关注。
16. 作为核心投资者，我希望研究事件逐项列出事实主张与证据，以便研究含义不会伪装成外部事实。
17. 作为核心投资者，我希望更正与撤回主动进入研究收件箱，以便不会继续依赖已经失效的研究结论。
18. 作为核心投资者，我希望旧简报、旧快照和旧回答保留原内容并提示后续更正，以便历史记录既不可篡改又不会误导当前判断。
19. 作为核心投资者，我希望看到重要性、置信度、相关性和信息增量的中文等级与简短依据，以便理解内容为何值得阅读。
20. 作为核心投资者，我希望系统在无法判断某个维度时明确显示“无法判断”，以便缺失信息不会被伪装成低分。
21. 作为核心投资者，我希望评分依据只引用当次输入证据和研究偏好，以便模型不能用记忆补充不可审计事实。
22. 作为核心投资者，我希望专业市场基线不受个人相关性影响，以便没有研究关注时仍能看到全局重要事件。
23. 作为核心投资者，我希望添加公司、行业、主题、研究事件或研究假设作为研究关注，以便系统持续跟踪我明确关心的对象。
24. 作为核心投资者，我希望在常规关注和重点关注之间切换，以便明确不同的个性化分发强度。
25. 作为核心投资者，我希望从已有收藏公司、收藏行业和自选股中选择导入关注，以便快速完成冷启动而不被自动导入。
26. 作为核心投资者，我希望导入项默认是常规关注，以便重点关注只能由我主动提升。
27. 作为核心投资者，我希望个性化研究雷达独立展示相关变化，以便个性化不会改变专业市场基线的内容和排序。
28. 作为核心投资者，我希望行业或主题关注只在存在明确实质影响时传播到下级公司，以便关注范围不会无控制扩大。
29. 作为核心投资者，我希望重点关注不通过层级传播自动继承，以便弱关系不能触发公司级紧急提醒。
30. 作为核心投资者，我希望查看内容为何进入个性化结果时能看到实际命中的研究关注、关系和当时级别，以便纠正未来结果。
31. 作为核心投资者，我希望暂停个性化时保留关注配置，以便恢复后无需重新建立关注。
32. 作为核心投资者，我希望清除研究偏好时删除全部研究关注但保留既有收件箱记录，以便隐私控制不破坏历史研究记录。
33. 作为核心投资者，我希望移除一个研究关注只影响未来排序和分发，以便历史记录不会被改写。
34. 作为核心投资者，我希望“稍后”只改变阅读状态，以便阅读管理不会被系统解释成兴趣。
35. 作为核心投资者，我希望“有用 / 噪声”只记录该次分发质量反馈，以便反馈不会偷偷改变全局事件评分或个性化画像。
36. 作为核心投资者，我希望研究收件箱以待处理、未读、稍后和归档组织内容，以便高效分拣研究材料。
37. 作为核心投资者，我希望列表只显示标题、两行摘要和重要性，以便快速扫描而不被标签和元数据淹没。
38. 作为核心投资者，我希望右侧以连续短研究稿阅读事实、影响、原因、后续观察和风险，以便保持完整阅读流。
39. 作为核心投资者，我希望证据、来源资格和修订记录默认折叠但可随时展开，以便兼顾阅读效率与核验需求。
40. 作为核心投资者，我希望同一内容只形成一份站内记录并标明最高分发渠道，以便紧急提醒和简报不会制造重复副本。
41. 作为核心投资者，我希望盘前、收盘和有实质增量的晚间简报按专业节奏到达，以便在关键时间形成研究摘要。
42. 作为核心投资者，我希望晚间没有达到门槛的信息增量时系统静默跳过，以便不收到无意义简报。
43. 作为核心投资者，我希望高重要性、高置信度、高信息增量且直接命中重点关注的事件触发紧急提醒，以便重要变化不会被普通内容淹没。
44. 作为核心投资者，我希望满足严格证据条件的重大待核实变化也能提醒并醒目标记风险，以便在不伪装成确认事实的前提下及时获知。
45. 作为核心投资者，我希望研究收件箱先成功写入再发送 Feishu，以便外部投递失败不会丢失权威记录。
46. 作为受邀私测用户，我希望 Feishu 提醒默认已经授权并启用，以便无需额外配置即可收到符合门控的副本。
47. 作为核心投资者，我希望可以关闭 Feishu 副本，以便主动控制外部打扰。
48. 作为核心投资者，我希望直接向研究智能体提出公司、行业、主题或假设问题，以便进行即时研究而不等待后台事件生产。
49. 作为核心投资者，我希望即时研究可以有界检索公开网页并引用当次证据，以便回答不局限于已有数据库对象。
50. 作为核心投资者，我希望即时研究发现的新材料不会同步改写全局事件，以便前台回答和后台权威生产保持隔离。
51. 作为核心投资者，我希望 Agent 遇到关键歧义时逐个询问，而次要缺口可以声明假设后继续，以便交互既准确又不中断。
52. 作为核心投资者，我希望系统拒绝买卖、持有、加减仓、仓位、入场价、目标价、止损价和订单计划，以便产品始终处于研究模式。
53. 作为核心投资者，我希望被拒绝执行性建议后仍能获得事实、证据、正反情景、风险和验证条件，以便问题仍有研究价值。
54. 作为核心投资者，我希望 Agent 不能直接写入权威状态或选择发送对象、渠道和时机，以便模型错误不能直接产生外部副作用。
55. 作为核心投资者，我希望明确且可撤销的单义自然语言指令可以直接执行，而含糊、批量、扩大发送或不可恢复操作需要二次确认，以便人在回路集中在真正需要授权的动作。
56. 作为系统维护者，我希望每次 Provider、LLM、数据库结算和外部投递都受全局资源许可约束，以便嵌套并发不能绕过上游限额。
57. 作为系统维护者，我希望交互级、时段关键级和后台级任务在每个资源池按确定性权重公平领取，以便交互速度与后台吞吐可以同时维持。
58. 作为系统维护者，我希望 PostgreSQL 是任务、许可、熔断和调度状态的唯一权威源，以便进程重启和重复唤醒不会改变业务事实。
59. 作为系统维护者，我希望 Redis 只承担至少一次唤醒，以便消息丢失、重复或 PEL 恢复不会成为任务真相。
60. 作为系统维护者，我希望所有重试都有明确的次数、时间预算和可重试分类，以便永久错误不会无限循环。
61. 作为系统维护者，我希望任务积压达到上限时按等级拒绝、合并或暂停，并保留原因和最老任务年龄，以便系统不会无界占用资源。
62. 作为系统维护者，我希望供应商、模型和投递渠道可以独立熔断、半开探测和恢复，以便一个外部依赖故障不会拖垮全部系统。
63. 作为系统维护者，我希望旧 Worker 的 fencing token 无法覆盖新 Worker 结果，以便租约接管不会破坏权威状态。
64. 作为系统维护者，我希望相同冻结输入和版本可以复用已校验的成功结果，以便重试和重放不会产生不必要的外部调用。
65. 作为系统维护者，我希望每次 Agent 运行记录身份、输入、能力、模型、工具、停止原因和资源消耗，以便能够审计而无需保存隐藏推理过程。
66. 作为系统维护者，我希望按来源时钟和产品时钟分别度量时效，以便快速处理旧数据不会被误判为达标。
67. 作为系统维护者，我希望每个来源、数据集和交易阶段独立记录达标率、p50/p95、降级率与积压年龄，以便私测后能校准真实目标。
68. 作为开发者，我希望在最高 application module interface 验收用户能力，以便测试不依赖内部实现细节。
69. 作为开发者，我希望 PostgreSQL repository contract test 验证历史、幂等、fencing、门控和调度不变量，以便数据库竞争行为可重复验证。
70. 作为开发者，我希望 C++ Worker 只测试生命周期和版本化信封映射，以便业务语义集中在 Web/Python module 而不重复实现。
71. 作为开发者，我希望 TuShare、Minishare、DeepSeek 和 Feishu 都有生产 adapter 与测试替身，以便外部故障组合无需真实调用即可验收。
72. 作为发布负责人，我希望硬门槛失败时阻断发布，而运行目标失守时产生可观测违约和确定性降级，以便正确性与性能目标不会混为一谈。

## Implementation Decisions

### 1. 产品范围与用户边界

- MVP 面向以个人身份使用产品、管理较集中 A 股组合的核心投资者，不建设机构多租户、团队协作或采购审计。
- 产品模式固定为 `research_only`。产品可以提供事实、证据、不确定性、方向性研究含义、正反情景、风险因素、判断条件和后续验证项，但不得结合个人资产或持仓给出买卖、持有、加减仓、仓位、入场价、目标价、止损价或订单计划。
- 专业市场基线、个性化研究雷达、研究收件箱、定时简报、紧急提醒、即时研究和 Feishu 副本全部属于 MVP，不得因工程拆票而移出范围。
- MVP 是完整能力集合，不由某一个端到端样例代表。实现可以渐进合并，但只有本文全部发布硬门槛和范围内验收项通过后，MVP 才可判定完成。

### 2. 专业市场基线的信息架构

- 专业市场基线采用“时段走廊”：盘前、盘中、盘后和前瞻是主工作阶段；以紧凑阶段按钮与下拉切换，不在页面堆叠大量固定按钮。
- 六类信息域固定为市场结构、资金与交易行为、公司信息、新闻与政策、预期变化和事件日历。信息域横向选择，显示当前阶段下的轻量数量上下文，不使用左侧纵向导航占据主要空间。
- 概览至少提供市场广度趋势、资金方向和关键事件节点三类图表，图表随阶段变化并与数据截止点、降级状态一致。
- 正文保留可点击证据时间线和详情入口。图表建立方向感，证据与来源解释负责追溯。
- 专业市场基线的内容集合与内部排序对所有用户一致，每个时段为全局高重要性研究事件保留固定展示容量。研究关注不能删除、降序或重排基线内容。
- 盘前使用上一交易日完整结构化数据、隔夜事件、晚间资金/预期及当日前瞻日历；盘后以当日已结算结构化数据和事件修订为主干；前瞻覆盖财报披露、分红、解禁、IPO、宏观数据和可从合格材料派生的日程。
- 盘中只展示实际可用且经过完整性、延迟和数据截止点校准的内容。未校准能力明确降级，不使用旧日线快照伪装实时，不承诺两分钟级结构化行情。

### 3. 数据源与 Provider module

- TuShare 与 Minishare 的目标接口访问和商业授权视为已满足，不建设权限审批或权利状态门控。Provider 仍必须声明其支持的 `datasetKey`、contract 版本、规范化规则版本和实际数据能力。
- 六类信息域的初始数据职责包括：
  - 市场结构：A 股日线与每日指标、核心指数、申万行业、主题/概念及经校准的盘中行情；
  - 资金与交易行为：个股/市场/行业/概念资金流、两融、龙虎榜、涨跌停和热度；
  - 公司信息：财务与业绩、公告、分红、回购、解禁、公司行动和董秘问答；
  - 新闻与政策：新闻、公告、政策法规、货币政策材料及其原始来源线索；
  - 预期变化：卖方盈利预测、评级、研报元数据及市场共识变化；
  - 事件日历：财报披露、分红、解禁、IPO、宏观数据、政策与交易制度节点。
- Python Provider/adapter 负责外部访问、分页、字段映射、单位和时间语义、来源权威选择、规范化、结果哈希与供应商错误映射；不得直接写 PostgreSQL。
- 后台采集必须与交互查询分开配置，不能复用 500 行、365 天等交互上限。Minishare 等列表接口必须持续分页到目标数据截止点，不能静默截断。
- 来源权威按“来源 × 数据集”配置。主来源缺失时只允许使用已声明的回退来源，并在结果中冻结权威策略版本、采用来源、佐证来源、选择理由和回退原因。MVP 不建设跨来源对账或来源投票。
- 所有 Provider 与测试替身共享一个版本化 `HomepageDataItemResult` interface。结果状态为 `success / degraded / empty / error`，数据质量状态独立为 `normal / degraded / isolated`。
- 结果信封必须固定请求与覆盖范围、缺失范围、实际数据截止点、规范化观测、来源断言、质量旗标、结构化错误、重试归类和重放上下文。供应商字段、单位猜测和供应商错误语义不得泄漏给 C++ Worker。
- 精确数值使用十进制字符串；禁止 `NaN`、`Infinity`、隐式单位和仅靠 `null` 推断缺失原因。
- 时间语义至少分离观测期间、上游截点、来源发布时间、实际数据截止点、规范化时间和入库时间。真实时刻保留来源时区并以 UTC 比较；交易日和报告期保持业务期间语义。
- 合法 `empty` 是不可重试的结算终态，可以没有修订，但必须证明请求范围已覆盖并保留实际数据截止点；是否通过门控由清单项的 `emptyPolicy` 决定。
- 未知错误默认可重试但受生命周期上限约束；配置、鉴权、请求非法、contract 不兼容、合法空结果和确定性规范化失败不得作为普通技术错误无限重试。

### 4. 数据观测与两层首页数据清单

- PostgreSQL 是首页数据、来源证据、修订、清单、任务和快照的唯一权威源；不引入第二事件存储或对象存储作为 MVP 真相。
- 数据观测身份由规范化主体、指标目录 ID、已排序维度和观测时段形成版本化稳定键。来源、抓取时间、当前值、质量和鲜度不参与事实身份。
- 来源断言按来源、数据集、来源记录身份和原始内容哈希幂等，保留可审计原始记录或必要完整正文、请求参数哈希、Provider 版本和来源时间；凭据、请求头和内部日志不得进入原始记录。
- 数据观测修订在规范化选值变化或上游明确更正时创建不可变替代链。普通重复值按观测、值哈希和规则版本复用；显式更正即使值回到旧值也建立新链节点。
- 每个修订固定一个选定来源、零个或多个佐证来源，以及必要的派生输入修订；当前修订指针只用于当前读取，历史清单、报告和 Agent 输入必须引用固定修订。
- 首页数据清单分为专业市场基线清单和个性化首页清单。基线清单无用户和父清单；个性化清单必须属于用户、固定一个已经通过必需项门控的基线清单，并只保存新增清单项，不复制或动态跟随父基线。
- 个性化清单直接冻结创建时的显式研究关注内容，不保存偏好指纹、单调偏好版本或其他首页身份替代键。
- 清单逻辑键由范围、定义版本、目标上下文及请求语义规范化生成；相同逻辑请求幂等复用，明确强制刷新通过新的请求随机量保留新历史。
- 清单项固定数据集、事实范围、要求版本、必需/可选、空结果策略和目标数据截止点；个性化追加项不得覆盖父基线同范围项。
- 清单项分离获取尝试和唯一不可变结算。获取尝试持有租约、心跳、fencing、重试和原始结果信封；结算固定采用的尝试、覆盖、实际数据截止点、质量、终态和完整修订集合。
- 清单门控是可重算投影：必需项尚未结算为 `PENDING`；必需项失败、降级或未达截止点为 `BLOCKED`；必需项达标且可选项正常为 `READY`；必需项达标但可选项失败或降级为 `READY_WITH_LIMITATION`。
- Provider 调用在事务外执行。结算事务必须校验租约与 fencing，幂等写入来源断言、数据观测和修订，写入一次清单项结算，重算门控，并在门控通过时幂等创建首页生成任务。
- 结果重建重放只读取既有清单结算和修订集合，不调用 Provider、不创建获取尝试或新修订；数据重新获取创建新的尝试或清单历史。
- 项目未部署且数据库只有 mock 数据，相关 schema 迁移直接删除旧临时首页数据和旧字段，不建设兼容回填、双写或长期双版本层。

### 5. 首页生成、快照与读取

- C++ `homepage-worker` 只负责领取、租约、心跳、重试、协作式取消和带 fencing 的原子结算。Web 首页 module 负责固定输入装载、业务生成和结果信封；C++ 不解释数据观测、清单项或页面区域。
- 首页数据清单是生成任务与首页快照的唯一业务输入身份。生成任务固定清单、全局激活序号、输入 contract、生成定义、payload schema 和 `PROMOTABLE / HISTORICAL_ONLY` 晋级模式。
- 只有父基线与个性化追加项组成的全部有效清单项都进入终态，且清单达到 `READY` 或 `READY_WITH_LIMITATION`，才创建生成任务；不能把仍在获取的可选项当作缺失。
- Web 在短只读、可重复读事务中装载任务、清单、父基线、清单项结算、固定修订集合及冻结偏好内容，稳定排序后按 RFC 8785 规范化并计算带算法前缀的输入哈希。
- 首页生成是无外部副作用的确定性转换；相同固定输入与生成定义必须产生相同 payload、数据覆盖摘要和哈希。生成期间不得读取当前偏好、当前观测修订、系统时间，或调用 Provider、LLM 和其他外部源。
- Worker 与 Web 的版本化内部 interface 只传任务身份、Worker 身份和十进制字符串 fencing token；返回 `generated / obsolete / retryable_failure / terminal_failure` 之一，并使用稳定错误码表达输入未就绪、依赖不可用、contract 不兼容和输入不变量损坏。
- repository 在单一写事务中重新校验任务、Worker、租约和 fencing，幂等插入不可变快照，按激活序号条件推进当前投影，并结算任务。已有结果字段不完全相同属于非确定性生成终态失败，绝不覆盖。
- 专业市场基线当前投影全局唯一，个性化当前投影按用户唯一；投影只按激活序号前进，不按生成时间或完成顺序选择，旧任务晚完成不得使当前快照倒退。
- 偏好修改、暂停/清除个性化、旧个性化投影失效、旧未完成任务取消和新个性化清单创建必须通过统一幂等事务 seam。新个性化快照就绪前回退当前专业市场基线。
- 首页读取信封必须提供来源范围、快照/清单身份、生成时间、按清单项表达的数据覆盖、个性化处理中、基线已更新和刷新中等语义；删除含义过载的首页级单一数据日期和模糊 `isStale`。

### 6. 研究事件候选、证据与修订

- 研究事件是全局共享、已经发生且对专业市场基线具有研究价值的一次可区分现实变化，不是新闻、公告、数据异常或 LLM 文本。
- 外部材料与合格数据观测先形成研究事件候选。代码按来源条目 ID、规范 URL 和内容哈希精确去重；LLM 对可能描述同一变化的材料做语义聚合，原始材料仍作为独立证据保留。
- 候选簇默认对应一个现实变化；只有材料明确包含多个可独立成立且时间或主体不同的变化时才拆分。聚合不确定时暂时分开，后续合并或拆分保留审计关系。
- 候选裁定前可执行有界证据补全任务，检索公开网页、反证和来源身份线索；任务结束后冻结证据集合，再执行一次裁定。裁定过程中不得动态加入证据。
- 每个候选簇单次 LLM 调用原子返回三态裁定、事件主体、必要拆分、逐项事实主张、证据身份与资格、独立性、研究含义、影响对象、不确定性、反证、缺口、核实条件和分层时间。
- 晋级要求“现实变化成立”和“研究价值成立”两道门槛。权威一手证据可以独立证明对应事实；否则需要事实采集链相互独立的证据交叉印证。来源身份真实不等于其对任意事实有证明资格。
- 交易所、监管机构、认证账号和可信接口使用系统提供的身份依据；公司网址可以通过注册域名的 ICP 备案主体与法定全称一致得到“大概率官网”，但该状态不自动赋予事实证明资格。
- 合格数据观测可以作为证据；降级、隔离、过期、单位未知或主体/期间不明的观测不能用于晋级。价格和成交量异常只能触发候选，不能独自证明现实变化。
- 每条事件事实主张绑定引用片段、来源指针或数据观测修订，并记录来源身份和证明资格；研究含义逐项引用事实主张并明确为推断。
- 晋级关闭当前候选并创建研究事件首个修订；暂缓保持开放并记录缺口、条件、观察窗口和下一检查时间；驳回终结当前候选与证据集合但保留记录。暂缓窗口结束且无增量时转为暂缓结束。
- 新独立来源、更高证明资格证据、更正/撤回/冲突、关键事实或主体变化、核实条件满足及观察窗口终点可以触发重裁定；转载、措辞变化、抓取时间变化和相同内容哈希不触发。
- 已晋级事件只通过不可变更正、重新核实或撤回修订变化，不能退回候选驳回。当前读取使用最新有效修订，历史产物保留当时内容并提示后续修订。
- 技术失败只形成技术暂缓和有界重试，不产生事件、影响对象或主动提醒；已有有效修订的更新失败继续服务原修订并显示核查更新中。

### 7. 四维评估与确定性门控

- 四维为重要性、置信度、相关性和信息增量，统一使用内部 `0–4 | null` 序数量表，不计算总分、不解释为概率。用户展示固定映射为 `0–1 低 / 2 中 / 3 高 / 4 极高 / null 无法判断`。
- 重要性只衡量变化若属实对专业市场基线研究判断的影响幅度、范围与持续性；不得因证据可靠、用户关注或刚刚发生而加分。
- 置信度衡量输入证据对核心事实和影响推断的支持，取核心主张最低可信程度；不等于数据质量或模型概率。
- 相关性衡量事件与用户显式研究关注的关系，不改变事件全局重要性。无研究偏好时返回无法判断，专业市场基线不因此被屏蔽。
- 信息增量衡量当前事件修订相对冻结的相关研究认知基线新增了多少会改变研究判断的实质信息；基线不完整时返回无法判断，不默认判高。
- 每个事件修订执行一次全局评估，原子返回重要性、置信度和信息增量；每位用户对该修订执行一次独立相关性评估。两类结果分别冻结输入、缓存、版本、重试，再由代码组合。
- 全局输入固定事件修订、事实主张、影响对象/路径、证据与资格、冲突、不确定性和相关研究认知基线；相关性输入另固定研究偏好快照与版本化对象关系。模型输入不得包含无关用户身份。
- 每维返回分数、1–3 条原子依据、引用 ID、结构化不确定性和一句中文解释。禁止总分、综合等级和渠道建议；代码校验 ID 存在、类型正确、引用闭合和要求的双边引用。
- 合法 `null` 是无法判断，不是技术失败。全局评估任一维结构非法或引用失败使整次调用技术失败；不得拼接不同调用/版本。相关性失败只阻断该用户个性化排序和提醒，不影响专业市场基线。
- 站内准入：有效事件修订且全局评估合法即可展示，可以包含无法判断，但必须说明原因。
- 定时简报门槛：重要性、置信度、信息增量均可判断且都不低于 2；相关性只影响个性化简报排序，不是专业市场基线简报准入条件。
- 普通紧急提醒门槛：四维全部可判断且都不低于 3，并直接命中用户明确研究偏好；个性化提醒还必须直接命中重点关注，常规关注或层级传播不能单独取得紧急提醒资格。
- 渠道优先级为紧急提醒、定时简报、仅站内；同一次门控只形成一个最高渠道站内记录，不制造低级重复记录。
- 暂缓候选专用紧急提醒要求：来源身份真实；至少一项证据有资格证明核心事实；重要性、相关性、信息增量均不低于 3；置信度为 1–2；直接命中重点关注；内容醒目标记待核实和缺口。匿名传闻、来源未核实或仅由异常数据触发的候选禁止主动提醒。
- MVP 不实现跨时间去重、冷却或频率约束。

### 8. 四维评估模型路由

- 全局评估与逐用户相关性评估固定使用 DeepSeek 官方同步 API 的 `deepseek-v4-flash` 非思考模式，温度为 0；端点不接受 0 时使用最低支持值。禁止工具调用、联网和模型自行补证。
- MVP 明确接受使用 DeepSeek 处理最小冻结研究输入的供应商数据风险，不把“不训练、留存期限、删除机制”的企业书面条款作为私测阻断项；不得发送用户身份、资产、持仓等无关信息。
- 全局评估输入最多 32K tokens、输出最多 3K tokens；相关性输入最多 8K、输出最多 1.5K。按确定性优先级裁剪并记录省略对象；必要输入缺失时返回无法判断，不猜测。
- 仅使用同步 API 和项目队列，不实现 DeepSeek Batch。相同冻结输入、模型参数、提示词、Schema 和校验规则版本可以复用已通过机器校验的成功结果；失败不缓存。
- 支持凭据池，但只有独立账号和独立额度算独立资源池；同账号多 Key 只用于轮换。评估记录保存非秘密凭据标识和用量，不保存 API Key。
- Schema、分值或引用闭合失败时最多进行一次结构修复重试；网络、超时、429 和 5xx 按时段关键级策略重试并可切换健康独立账号。耗尽后不切模型、不拼响应、不生成兜底分数。
- MVP 不设应用日/月预算、用户配额、余额检查或成本门控；每次调用记录输入、缓存命中和输出 token，并记录所有重试。

### 9. 显式研究关注与冻结偏好

- MVP 个性化只来自用户明确建立的研究关注，不采集、复制或派生查看、搜索、展开、稍后、有用或噪声等行为兴趣。
- 研究关注对象类型包括公司、行业、主题、研究事件和研究假设；级别只有常规关注与重点关注。新增和导入默认常规，提升重点必须由用户主动操作。
- 常规关注进入个性化研究雷达、研究收件箱和定时简报；重点关注在此基础上获得紧急提醒候选资格，但仍必须满足重要性、置信度和信息增量门槛。
- 专业市场基线保持完整且对所有用户一致。个性化研究雷达是独立区域，相关性可以增强排序和分发，不能改变全局事件是否存在或专业市场基线内部排序。
- 层级传播使用结构化对象关系与事件影响关系，不由 LLM 猜测归属。行业/主题关注只在公司事件对上级对象有明确实质影响时形成较弱相关性；关注身份与重点级别不传播。公司关注可以向显式所属行业传播弱相关性。
- 首次使用不弹强制问卷，直接进入专业市场基线。研究雷达空状态提供添加关注和从收藏/自选导入；导入按收藏公司、收藏行业和自选股分组多选，不预选、不自动导入、不反复催促。
- 研究偏好页面只管理显式关注、个性化总开关以及紧急提醒、定时简报和外部提醒副本的用户级开关；不提供对象级渠道矩阵或行为设置。
- “暂停个性化”保留关注；“清除研究偏好”经精确影响提示和二次确认后删除全部关注；移除单项只影响未来。暂停和单项移除提供当场撤销。
- 内容内“不再关注”必须按实际命中的关注精确执行；多项命中时由用户选择，不能猜测。个性化解释按需显示命中关注、关系和当时级别，不在列表常驻。
- PostgreSQL 保存可变当前态，并通过一个窄 module interface 冻结不可变研究偏好快照。快照包含 contract 版本、启用状态、用户级分发开关、稳定排序的规范化关注集合、冻结时间和内容哈希；相同内容可幂等复用。
- 不建立单调偏好版本、偏好指纹、行为历史副本、兴趣线索、衰减权重或行为传播表。研究偏好快照只供相关性评估与分发门控，首页清单使用自己直接冻结的偏好内容，两者不共享输入身份。
- 偏好变化只作用于后续冻结和后续进入评估/分发的内容；已经形成待发送记录或进入队列的内容继续使用冻结结果，不做在途回查。
- 个人信息删除优先于完整历史重放：删除可识别偏好快照和解释输入，历史收件箱记录可以保留并标记个性化输入已删除，不承诺重放已删除的相关性判断。

### 10. 研究收件箱、简报、提醒与 Feishu

- 研究收件箱是主动分发的站内权威记录，采用三栏分拣台：左侧待处理/未读/稍后/归档，中间事件列表，右侧连续阅读。
- 列表项只展示标题、两行内摘要和重要性。待核实、更正等必要语义写入标题；未读使用轻量视觉提示，不堆叠公司、渠道、时段、相对时间、反馈和其他评分标签。
- 右侧正文按连续短研究稿组织发生了什么、对判断的影响与原因、后续观察和仍需留意；标题上方只保留研究对象、事件状态、最高渠道和时间，标题下以低强调文字显示四维等级。
- 证据、来源资格、修订记录、AI 标识与外部副本状态放在正文后；证据和修订默认折叠，可按需展开。
- 未读/已读/稍后/归档是单条收件箱记录的阅读状态；打开未读即已读并可手动恢复未读。“有用 / 噪声”只记录分发质量反馈，不修改全局评估或个性化。
- 同一门控结果只生成一条站内记录并标明最高渠道。更正与撤回必须产生新的站内通知，不覆盖旧记录。
- 盘前简报在交易日 08:50 写入，覆盖上一交易日完整数据、隔夜事件和当日前瞻；收盘简报在 16:45 写入，覆盖首批收盘行情、指数和行业结构；晚间增量简报最早 22:50，仅在资金、预期或事件达到增量门槛时发送，否则静默跳过。
- 未完成盘中数据校准前不生成固定盘中简报；盘中只处理具备合格证据的事件与紧急提醒。前瞻内容并入盘前简报，重要日程修订走研究事件门控。
- 简报候选范围、必显更正/撤回、渠道、容量和收件箱提交顺序由确定性代码冻结；Agent 只在冻结集合中组织叙事，不得新增事实或删除必显内容。
- 对受邀私测用户，Feishu 渠道在账号开通时视为完成持续预授权并默认启用。通过确定性门控的紧急提醒、定时简报、更正和撤回通知在站内提交后自动发送 Feishu 副本，无需逐条确认。
- Feishu 副本只包含必要标题、理由、状态和站内链接，不成为权威记录。发送失败只重试副本，不回滚或复制站内记录，不自动改投其他渠道。
- 用户可以关闭 Feishu 副本。恢复已关闭渠道属于扩大外部分发，应展示影响并由用户确认；Agent 不直接调用 Feishu，也不选择收件人、渠道或时机。

### 11. Agentic Workflow、即时研究与人在回路

- Agent Runner interface 接收一次冻结的 Agent 执行边界：目标、输入快照与幂等身份、能力集合、网络策略、步骤/时间/Token/成本/工具调用/并发上限；返回结构化结果、证据缺口、停止原因和审计摘要。
- Agent 可在授权边界内选择 Skill、工具、顺序、提前结束和共享预算的并发子任务；不能扩大目标、能力或预算，不能安装/修改 Skill、取得新凭据、执行未登记命令或改变停止条件。子任务继承能力并共享父预算，不能扩权扩容。
- Deterministic Controller 是权威写入、领域状态迁移、契约验证、意图处理、分发门控和外部投递的唯一 seam。Agent/LLM 承担事件裁定、四维评估和简报表达的语义判断；代码不重复扮演业务裁判，但必须校验 Schema、引用闭合、版本和执行边界。
- Agent 可以通过受控抓取访问公开 HTTP(S) 网页，不按可信域名白名单预拦截；不得访问本机/内网、使用应用凭据或绕过登录、付费墙和访问控制。网页材料先是未裁定候选，不能直接成为权威对象或主动分发内容。
- 后台专业市场基线、研究雷达、收件箱、简报和提醒只能消费已经结算的数据观测修订、研究事件修订、证据、评估和冻结偏好。临时网页材料必须先通过候选生产和确定性写入。
- 即时研究是例外：可以直接使用当次公开网页证据形成用户回答，不为复用而等待或强制匹配权威对象。恰好命中既有权威对象时可以引用；新发现只在响应后异步、幂等回灌候选种子，不同步修改全局状态。
- Pi Agent Harness 负责研究会话持久化、恢复和上下文压缩。关键歧义逐个询问，次要缺口声明假设后继续；后台任务不等待用户，缺少必要输入时结构化结束或暂缓。
- 持续追踪计划必须固定待验证事实、合格证据、触发条件、检查频率、到期时间和资源上限。全局事件核实计划可由代码自动激活；个性化计划只能来自已有研究关注或用户当次确认。计划命中只产生证据或候选修订。
- 人在回路只用于用户自身未预授权副作用和高风险操作，不建设运营人工审核队列。明确、单义、可撤销的自然语言指令可以作为确认；含糊对象、批量变更、扩大发送、访问受限资源和不可恢复动作必须展示精确影响并二次确认。
- `research_only` 必须在所有同步、异步、Agent、Skill、定时任务、附件和外部分发路径由确定性代码强制。拒绝执行性部分后仍返回合规研究内容，不追问用户持仓、资产或风险偏好来生成个性化动作。

### 12. 分级调度、资源许可和可靠执行

- 调度等级固定为 `INTERACTIVE / TIME_CRITICAL / BACKGROUND`。每个执行资源池以 PostgreSQL 原子 claim 按 `5:3:1` 确定性加权领取；空闲容量可借用，高等级任务不抢占已运行任务。
- 交互级包括即时研究、明确刷新/重试和无快照时的个性化生成；时段关键级包括基线必需采集、事件生产、四维评估、提醒、简报和站内提交；后台级包括可选数据、无人等待的个性化追加、回填、重放和维护。
- 同等级先按目标完成时间紧迫区间，再按 `fairnessKey` 加权轮转，最后按创建时间。用户任务使用用户公平键且同用户同资源池默认最多运行一个；系统任务按基线、事件和简报使用独立公平键。
- 执行资源池至少区分供应商账号与能力、本地规范化/数据库结算、LLM 账号/模型、首页/简报生成和 Feishu 投递。
- Worker 线程限制任务并发；每次 Provider、LLM、数据库结算和投递调用还必须取得 PostgreSQL 短期资源许可。分页、批处理和嵌套并发不得绕过许可；等待退避或下一阶段时释放许可。
- TuShare 的公开调用频率按账号全局执行；未公开限额的外部数据源和 LLM 初始并发为 4、私测硬上限 16，投递初始并发 2、硬上限 8，可按资源池覆盖。
- 连续成功至少 20 次、持续健康至少 5 分钟且 p95 未显著上升时并发加 1；429 立即减半并遵守 `Retry-After`；单次超时减 1；p95 连续两个窗口超过健康基线两倍时减 1；降低后至少冷却 5 分钟，陈旧控制状态保守回到 1。
- 任务准入先按幂等键合并。设资源池硬并发为 C，交互/时段关键/后台待领取上限分别为 `4C / 20C / 50C`；交互超预算明确返回繁忙，时段关键停止重复周期任务并保留仍有意义的最新幂等任务，后台暂停准入并合并范围。
- C++ Worker 只按本地剩余容量领取，进程内队列最多为执行线程数两倍。所有拒绝、合并、过时和积压结论保留原因与最老任务年龄。
- 只有结构化可重试技术失败重试。交互级最多 3 次且总计不超过 120 秒；时段关键最多 5 次且不超过 20 分钟或目标完成时间；后台最多 6 次且不超过 24 小时；外部投递最多 5 次且不超过 30 分钟。
- 数据库保存 `nextAttemptAt`，使用指数退避和随机抖动，`Retry-After` 是最早恢复时间。重试保留等级但同目标时间下排在未尝试任务之后。
- 同资源池连续失败 5 次或最近 20 次失败率达到 50% 进入熔断；429 与 `Retry-After` 可直接熔断。等待序列为 60 秒、2 分钟、5 分钟、10 分钟、30 分钟，半开只允许一个探测。鉴权、配置和 contract 不兼容为人工修复的配置阻断，不自动半开。
- PostgreSQL 是任务生命周期、许可、并发、熔断和下一次尝试时间的权威源；Redis 只提供至少一次唤醒，重试保留原 PEL 消息，不发布替代消息。
- 共享 C++ 任务生命周期 module 通过强类型配置、repository 和 executor interface 提供领取、续租、结算、fencing 与协作式取消；业务 Worker 只解析其外层版本化信封。

### 13. 分阶段降级

- 必需首页数据未达目标数据截止点：不生成新快照，继续服务旧当前快照并显示实际数据截止点。
- 可选首页数据失败、降级或合法空结果：清单达到 `READY_WITH_LIMITATION` 后生成新快照并展示限制。
- 事件规范化或候选裁定失败：保留候选和技术记录，不创建研究事件。
- 全局四维评估失败：不创建新的定时简报或紧急提醒，旧有效内容保持。
- 单用户相关性失败：不影响专业市场基线，但禁止该用户个性化排序和紧急提醒。
- 简报生成失败：研究事件仍可在站内工作台读取，不拼接未经验证的替代简报。
- Feishu 失败：研究收件箱保持权威，只重试 Feishu 副本。
- 降级只能降低可用性或时效，不能降低数据质量、证据资格、引用闭合、`research_only` 或确定性门控要求。

### 14. 时效与容量目标

- 时效采用双时钟：来源时钟从可信来源发布时间或系统首次确认上游可用开始；产品时钟按盘前、盘中、盘后和前瞻就绪点。二者都必须同时检查实际数据截止点。
- 每个“来源 × 数据集 × 交易阶段”独立记录达标率、p50/p95、降级率和积压年龄。数字是私测运行目标，不是永久 SLA；失守必须记录、告警和执行对应降级。
- 数据层初始目标：

| 每日指标及较晚盘后结构 | 15 分钟 | 交易日 17:15 |
| 资金流、龙虎榜等晚间数据 | 15 分钟 | 交易日 19:20 |
| 卖方预期变化 | 20 分钟 | 交易日 22:20 |
| 最晚热度数据 | 15 分钟 | 交易日 22:45 |
| 次日两融数据 | 10 分钟 | 下一交易日 08:45 |
| Minishare 新闻、公告、政策候选 | 2 分钟 | 连续更新 |
| 前瞻日历 | 30 分钟 | 每日 07:30 完成验证 |

- 处理与分发初始目标：

| --- | ---: |
| 交互级任务等待领取 | 2 秒 |

- 任一产品就绪点或紧急提醒目标失守记录时效违约；最老任务年龄达到预算 50% 预警，达到 100% 严重告警并降级；必需源熔断、许可 module 不可用或调度份额长期偏离为严重告警。
- 私测统计按滚动 20 个交易日汇总，不能用平均值掩盖 p95 失守。

### 15. 审计、安全与隐私

- 每次 Agent 运行保存任务身份和发起者、父子关系、输入快照/哈希、执行边界、Skill/工具/模型版本、工具调用摘要和来源、结构化输出、校验结果、停止原因、Token/成本/耗时及后续领域对象或意图记录。
- 不保存隐藏推理过程，不要求永久保存全部网页全文；来源断言和事件证据按相应不可变契约保留必要完整记录或引用片段。
- 内部 HTTP interface 同时校验内部密钥和数据库执行资格；密钥不能代替任务状态、worker、租约和 fencing 校验。
- Provider、模型和 Feishu 凭据不得进入任务消息、原始记录、日志、审计 payload 或模型输入；只保存非秘密凭据标识。
- 模型输入最小化，不包含用户身份、资产、持仓、成本和与评估无关的个人信息。
- 研究偏好属于个人信息；用户可以查看、修改、暂停、清除。删除时隐私优先于个性化历史完整重放，专业市场基线和既有收件箱事实记录不删除。
- MVP 不建设运行时数据权利或系统整体合规资格判断，但发布前仍需完成适用于真实私测形态的证券、金融信息、生成式 AI、算法、隐私、AI 标识、投诉纠错和安全事件流程确认。TuShare/Minishare 商业授权已满足，不列入待完成门槛。

### 16. 发布判定层级

发布判定分为“发布硬门槛”和“私测运行目标”两层：

- 硬门槛失败时阻断发布，不允许用降级绕过。
- 运行目标必须实现观测、告警和确定性降级，但初始数字可以基于真实私测水位校准；单次失守不等于整个版本不可发布。

发布硬门槛包括：

1. 全部 schema、类型检查、contract test、repository contract test 和规定的跨 module 场景通过。
2. 旧 mock 首页 schema 和冲突语义完成直接迁移，不存在依赖未定义旧字段的兼容旁路。
3. Provider contract 的状态、质量、覆盖、时间、错误和重放字段完整，TuShare/Minishare/测试替身共享契约测试。
4. 清单、观测、来源、修订、任务、快照和收件箱满足幂等、fencing、不可变历史和投影只前进不变量。
5. 必需/可选项、合法空结果、数据截止点及 `READY_WITH_LIMITATION` 门控全部通过验收。
6. 候选三态、证据资格、引用闭合、更正与撤回不可变链通过验收；技术失败不能创建权威事件。
7. 四维评估固定 20 个全局样例和 20 个相关性样例，在最多一次结构修复重试后，Schema、`0–4 | null`、引用闭合和禁止字段 100% 通过。
8. `research_only` 在同步、异步、Agent、Skill、定时、简报和 Feishu 路径拒绝所有执行性投资指令。
9. Agent 无权威写入、门控、收件人/渠道/时机选择或直接外部发送权限；所有副作用经过 Deterministic Controller。
10. 研究收件箱先于 Feishu 写入；Feishu 重试、失败和熔断不回滚或复制站内记录。
11. 分级调度、许可、背压、重试与熔断不能被分页、嵌套并发或多 Worker 绕过。
12. 审计字段、稳定错误码、资源用量、数据截止点和分段时效指标完整可查询，不保存凭据或隐藏推理过程。
13. 与真实私测形态相关的外部合规确认、用户协议、隐私与 AI/算法说明、AI 标识、投诉纠错、删除和安全事件流程完成；TuShare/Minishare 授权视为已完成项。

## Testing Decisions

### 1. 测试原则与 seam

- 测试只断言 module interface 的外部行为、持久化事实、版本化信封和可观察副作用，不测试私有函数、内部调用顺序或可替换实现细节。
- 用户能力在最高 application module interface 验收：专业市场基线读取、研究事件结算、四维评估、研究偏好冻结、个性化评估、收件箱提交、简报/提醒门控和即时研究意图处理。
- PostgreSQL 可替代依赖直接使用本地 PostgreSQL contract test，不把 repository shape 暴露到 application interface。测试覆盖竞争、事务、唯一约束、fencing、不可变历史、门控和投影。
- 跨进程自有能力通过版本化内部 HTTP interface 与 Redis 唤醒测试。生产使用 HTTP/Redis adapter，测试使用内存 adapter 或测试服务器；权威业务状态始终从 PostgreSQL 断言。
- TuShare、Minishare、DeepSeek 和 Feishu 等真实外部依赖使用注入 port；生产 adapter 与 mock/脚本化 adapter 构成真实 seam。测试替身必须覆盖成功、降级、空结果、错误、超时、限流、重复响应和 contract 不兼容。
- C++ Worker 测试只覆盖共享生命周期、外层信封、HTTP 映射、响应大小、取消、重试和 repository 结算；Provider、事件、首页 payload 和 LLM 语义只在其所属 Web/Python module 测试。
- 跨 module 场景数量保持少而有代表性，用于验证组合和责任交接，不重复穷举各 module 已覆盖的组合。
- 本项目不进行浏览器验证。页面行为通过现有 UI/application contract 测试、渲染结构测试和静态检查验证；所有 Web 测试放在统一测试目录。

现有 prior art 包括首页快照读取与查询隔离测试、定时任务投递契约测试、证据上下文测试、Agent Runtime 策略测试、C++ repository PostgreSQL contract test 和 Docker 故障集成测试。新测试应深化这些 seam，而不是在调用方复制内部实现测试。

### 3. 跨 module 验收场景

以下场景均必须实现，且共同覆盖组合行为；任何一个都不是 MVP 范围的替代定义。

1. **盘前全局基线**：上一交易日结构、隔夜事件和前瞻日历结算为基线清单，生成四阶段六域读取中的盘前内容；无研究关注用户得到与其他用户相同的基线集合和顺序。
2. **盘后结构化更新**：必需行情与行业结构达标、可选资金流降级，生成 `READY_WITH_LIMITATION` 新快照，数据覆盖准确，旧快照保留且投影只前进。
3. **公司事件与个性化分发**：公告/新闻形成候选，证据裁定晋级，完成全局评估；直接命中重点关注后写入紧急提醒站内记录，再发送 Feishu 副本。
4. **暂缓重大变化**：合格但冲突的证据形成暂缓候选，满足专用阈值时以待核实状态提醒；匿名或来源未核实版本被阻断。
5. **更正与撤回**：已分发事件出现权威更正后创建新修订，当前阅读更新、旧简报提示、收件箱新增更正通知、Feishu 发送副本，原历史不覆盖。
6. **偏好变化并发**：个性化首页生成途中用户移除关注；统一事务失效旧投影和任务，旧 fencing 不能提交，新快照就绪前回退基线，已进入发送队列的旧内容不回查。
7. **外部依赖故障**：Minishare 限流、DeepSeek 超时和 Feishu 故障分别进入独立资源池退避/熔断；基线、旧评估和收件箱按阶段降级且互不回滚。
8. **即时研究隔离**：用户询问公开公司事件，Agent 有界检索并直接回答；执行性价格要求被拒绝；发现的新证据只异步创建候选种子，不同步生成事件或提醒。
9. **调度饱和**：大量后台回放与时段关键任务积压时，交互即时研究仍获得许可；公平权重、背压、积压原因和时效违约均可观测。

## Out of Scope

- 自动交易、订单生成以及针对个人的买卖、持有、加减仓、仓位、入场价、目标价、止损价或执行计划。
- 读取个人资产、现金、持仓、成本或风险偏好后生成个性化投资动作。
- Level-2、逐笔成交、实时盘口、海外全品种和收费研报正文。经校准的普通实时/分钟能力可以支持本文盘中基线，但不扩展到上述专业行情范围。
- 机构多租户、团队协作、研究权限、采购与合规审计工作台。
- 行为兴趣个性化：查看/搜索/展开行为采集、兴趣线索、衰减权重、兴趣传播、自动/半自动创建研究关注和行为设置界面。
- 单个研究关注的渠道矩阵；MVP 只有研究关注级别和用户级分发开关。
- 跨时间去重、通知冷却和频率约束。
- 跨来源对账、来源投票、统一质量总分和复杂质量评分模型。
- 运营人工复核与异常处置工作台；可判定异常由确定性流程暂缓、阻断、重试或降级。
- 运行时数据权利或系统整体合规资格判定、数据权限审批和 TuShare/Minishare 权利台账。两方授权视为已完成。
- 网页提示注入识别、隔离和标记。
- 面向真实投研价值的真人工作流基线、配对评测、真实反馈阈值和质量回溯工作台；固定机器契约验收仍属于 MVP。
- DeepSeek Batch、多模型投票、模型级质量回退、应用预算/余额/成本门控。
- 让免责声明代替服务端 `research_only`、证据、引用或分发控制，或允许 Agent 绕过 Deterministic Controller。

### 实施纪律

- 所有工程 Issue 必须引用本文的相关 Implementation Decisions、Testing Decisions 和验收 ID，并说明其前置依赖。
- module interface 是调用方与测试共同使用的 seam；复杂度应隐藏在深 module 中，不向调用方暴露 Prisma、供应商字段、Worker 运行字段或 LLM 原始语义。
- 一个真实 seam 应至少有生产 adapter 和测试 adapter。不要只为“以后可能替换”创建无行为价值的薄接口。
- 文档、注释、测试名称和用户可见内容使用项目既有中文领域词汇；涉及中文的文件读写必须显式使用 UTF-8。
- Web 测试统一放在项目约定的测试目录；本项目不进行浏览器验证；页面不得添加 eyebrow。
